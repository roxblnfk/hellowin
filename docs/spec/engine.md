# Движок (backend)

Статус: **реализовано** — сцена и стадии тыкв, очередь переходов с идемпотентностью, сброс, RPC `state`, метрики,
игроки и их статистика, периодический процесс (тикер), таблица лидеров, летуны, фигурки игроков на поле, сюжет
(готовность сцен, переход по кнопке, финал и разоблачение, сова, пауза, зомби проклятого мира), роль
модератора (сброс — только ему), костёр (элемент `bonfire`: порог и стадии по сценам, `locked`, реплики совы), летуны
по сценам с пустыми наборами и `wobble` летучих мышей, магический круг финальной сцены (элемент `circle`: свой порог и
стадии, `locked` вне шага финала 0, готовность финальной сцены, `not ready` и `force` у шага финала 1), червяки
(`worm`) финальной сцены — наземные цели по лужайке, аптайм RoadRunner (`startedAt`) и разбегание фигурок на шаге
финала 2, свой набор летунов проклятого мира (`HELLOWIN_FLYER_KINDS_CURSED`) и светлячки (`firefly`), множитель
порогов модератора (`k`, «Сюжет») и число игроков на поле (`online`), лимиты RPC по игроку («Лимиты запросов»), бар
— сцена 0 со стойкой, кружками, чоканьем и целью бара («Бар»), мухи (`fly`) — летуны бара.

## Периодический процесс (тикер)

Летунов и таблицу лидеров двигает время, а не запросы игроков, — нужен процесс с расписанием.
Это плагин RoadRunner `service` (`.rr.yaml`, `service.ticker`): RoadRunner держит один долгоживущий процесс
`php app.php hellowin:ticker` и перезапускает его при падении (`restart_sec`). Процесс — то же приложение Spiral
в консольном режиме: KV, локи, метрики и публикация в Centrifugo идут по goridge RPC к плагинам, как из воркеров.

Цикл: раз в 200 мс (`--step`) — удержать лизинг, выполнить всё, что пора (`Ticker::tick(now)`), уснуть. Расписание —
в памяти процесса: после рестарта начинается заново, а не догоняет пропущенное. Сбой одной работы пишется в лог и не
останавливает цикл.

Почему не дублируется:

- процесс вне пулов воркеров: `rr reset`, рестарт или увеличение пулов его не трогают и вторую копию не создают;
- **лизинг** — RR-лок `ticker` с TTL 5 с, продлевается раз в секунду. Тикает только его владелец; вторая копия
  (перекрытие при рестарте, ручной запуск `hellowin:ticker`) ждёт, пока первая перестанет продлевать.

Альтернатива — самоперепланирующаяся задача RR jobs с задержкой: годится, но цепочка рвётся при потере задачи
(memory-очередь теряет её на рестарте) и требует внешнего «запала» и ключа идемпотентности тика против двух цепочек.
`service` проще объяснить и показывает ещё один плагин RoadRunner.

Работы тикера:

| Работа | Когда | Что |
|---|---|---|
| Запуск летуна | случайно раз в `HELLOWIN_FLYER_INTERVAL` мс; первый — через интервал после старта; на паузе пропускается | `FlyerFactory` (набор сцены или редкий) → ключ летуна + индекс → событие `flyer` → `hellowin_flyers_launched_total{depth}` |
| Запуск зомби | случайно раз в `HELLOWIN_ZOMBIE_INTERVAL` мс, своё расписание; только в проклятом мире (`finale` = 5), при включённых зомби и без паузы | `ZombieFactory` → как летун: ключ + индекс → событие `flyer` (`kind: zombie`) → `hellowin_flyers_launched_total{depth}` |
| Учёт улетевших | каждый тик | просроченные из индекса → под локом `flyer:{id}` ключ ещё есть → удалить, `hellowin_flyers_escaped_total{depth}` |
| Бар: розлив и «взять» | каждый тик | `BarService::tick`: в баре — налитая кружка с наступившим `until` ставится на стойку (`mugs`), если места есть — следующий розлив (`pour`); фигурки с наступившим `takeAt` берут кружку под локами `walkers` → `bar` (`take`, `bar-empty`); см. «Бар» |
| Чоканья по клику | каждый тик | фигурки `hellowin:walkers` с наступившим `clink.dueAt` → под локом `walkers` проверка цели, запись сбрасывается → событие `clink`; см. «Фигурки на поле», «Чоканье по клику» |
| Фигурки: вход и уход | раз в секунду | presence канала → новые игроки с `look` выходят на поле (`walker`), давно отключённые уходят (`leave`) → gauge `hellowin_walkers`; см. «Фигурки на поле» |
| Таблица лидеров | раз в `HELLOWIN_LEADERBOARD_INTERVAL` мс | игроки по индексу → `Leaderboard::top` (`HELLOWIN_LEADERBOARD_SIZE`) → ключ `hellowin:leaderboard` → событие `leaderboard` (с `online` — числом фигурок `hellowin:walkers`) → gauge `hellowin_players`, `hellowin_players_registered` |

Ранжирование — очки за летунов, затем «добитые» тыквы, затем клики; игроки без единого действия не попадают. Событие
публикуется на каждой сборке, даже без изменений: новый клиент получает таблицу в пределах интервала, а сразу —
из RPC `me` (последняя сборка из ключа).

## Летуны

Правила — [`scenario.md`](scenario.md), «Летуны»; события и RPC — [`protocol.md`](protocol.md).

- **Запуск** (тикер): глубина — равновероятно из `0..N-1` (летун из куста — глубина куста), N — длина `HELLOWIN_FLYER_DURATION`; время полёта и очки
  берутся по глубине (`HELLOWIN_FLYER_DURATION`, `HELLOWIN_FLYER_POINTS`: дальше — медленнее и дороже). С вероятностью
  `HELLOWIN_FLYER_BUSH_CHANCE` летун взлетает из случайного куста (`bushes` в `app/config/hellowin.php`; нет кустов —
  только край): из точки куста вверх и за верхний или боковой край через экран. Иначе — из-за левого или правого края
  (четверть — из верхнего угла) за противоположный, в небе. С вероятностью `HELLOWIN_FLYER_ARC_CHANCE` полёт — дуга
  через `via` (квадратичная кривая), иначе прямая. Точки за краем — `-8` / `108`. Генератор — `FlyerFactory`
  с инъекцией `Randomizer`: в тестах траектории детерминированы. Вид — из набора текущей сцены (`HELLOWIN_FLYER_KINDS`);
  пустой набор — обычного летуна нет, запуск тикера пропускается (редкий летун сцены по-прежнему выпадает с его шансом).
  Летучие мыши (`bat`) получают `wobble` (`Domain/Flyer/Wobble`): `amp` — случайно 3–8 % экрана, `waves` — 2–5 полных
  колебаний за полёт, до десятых; диапазоны — константы `FlyerFactory` (`WOBBLE_AMP`, `WOBBLE_WAVES`), не env: это вид
  траектории, а не число игры. У остальных видов поля нет, кроме червяков, светлячков и мух.
- **Проклятый мир** (`story.cursed()`, шаг финала 5) берёт вместо набора сцены свой — `HELLOWIN_FLYER_KINDS_CURSED`
  (один набор через запятую, без `;`); `FlyerService` передаёт флаг в `FlyerFactory::launch(now, scene, cursed)`. До
  шага 5 финальная сцена летает своим набором из `HELLOWIN_FLYER_KINDS`. Редкий летун — по-прежнему по сцене
  (`HELLOWIN_FLYER_RARE`, по умолчанию у финала его нет). Пустой набор — как пустой набор сцены. Пауза останавливает и
  этот набор; зомби идут отдельно, по переключателю `zombies`.
- **Светлячки** (`firefly`) — обычные летуны (край или куст, прямая или дуга), но глубина — только 1–2
  (`FIREFLY_DEPTHS`, ограничено числом глубин): из куста вне этих глубин светлячок не взлетает — путь берётся с края,
  глубина — равновероятно 1 или 2. Длительность — глубины, очки — `HELLOWIN_FLYER_FIREFLY_POINTS` на любой глубине.
  `wobble` вялый: `FIREFLY_AMP` 2–5 % экрана, `FIREFLY_WAVES` 1,5–3 (меньше и реже, чем у мышей) — плывёт, а не мечется.
- **Червяки** (`worm`) — обычный вид набора сцены (по умолчанию — финальной), но наземная цель: `FlyerFactory` берёт
  зону `walk` и выбирает две точки лужайки на 12–25 % экрана друг от друга, обе вне эллипса грядки и так, чтобы прямая
  между ними её не пересекала (`WalkZone::route` — без обхода; 20 попыток, иначе отрезок внизу лужайки). `depth` 1,
  длительность и очки глубины 1, без `via` и `bush`, `wobble` поменьше (`WORM_AMP` 0,8–2, `WORM_WAVES` 3–6). От
  проклятого мира и переключателя `zombies` не зависит; набор с `worm` без зоны — ошибка конструктора.
  На паузе модератора (`paused` в сюжете) тикер не запускает никого, расписание идёт дальше.
- **Мухи** (`fly`) — вид набора бара (сцена 0): `FlyerFactory` берёт `walk.bar` (`BarLayout`) и выбирает обе точки
  внутри прямоугольника `walk.bar.area`, отступив `FLY_INSET` 3 % от его краёв (чтобы `wobble` не выносил муху из
  зала), не ближе `FLY_MIN_LENGTH` 15 % друг к другу (20 попыток, иначе последние); препятствия бара не учитываются. С
  вероятностью `FLY_PERCH_CHANCE` 0,3 (константа, не env: вид траектории) — `via` над стойкой: `x` — случайно в
  `walk.bar.counter` `x1..x2`, `y` — на 4–10 % выше линии `counter.y` (`FLY_PERCH_RISE`, не выше `area.y1`), и
  `perch: true`; иначе без `via` и без `perch`. `depth` 1 (ограничено числом глубин), без `bush`, длительность —
  `HELLOWIN_FLYER_FLY_DURATION`, очки — `HELLOWIN_FLYER_FLY_POINTS`, `wobble` `FLY_AMP` 3–6, `FLY_WAVES` 6–10. `perch`
  хранится с летуном. Набор с `fly` без `walk.bar` — ошибка конструктора.
- **Редкие и особые.** С вероятностью `HELLOWIN_FLYER_RARE_CHANCE` запуск тикера — редкий летун сцены
  (`HELLOWIN_FLYER_RARE`); его же модератор запускает кнопкой (RPC `flyer.special`, виды `witch`, `roadrunner`, и на
  паузе). `roadrunner` бежит по горизонту: `from`/`to` за левым и правым краем на высоте `horizon`
  (`app/config/hellowin.php`), `depth` 0, без дуги и куста, время — как у ближней глубины (быстрый), `points` 0; выстрел
  по нему всегда промах, ключ не удаляется — летун улетает и учитывается как улетевший. Остальные особые (`witch`) —
  с края, на случайной глубине, очки `HELLOWIN_FLYER_RARE_POINTS`; сбитая ведьма — реплика `witch-down` с игроком.
- **Зомби** проклятого мира — тоже летуны (`kind: zombie`), чтобы выстрел, учёт улетевших, очки и метрики были общими.
  Путь (`ZombieFactory`): по лучу из центра эллипса грядки `walk.patch` под случайным углом — от точки на краю грядки
  до выхода за прямоугольник лужайки `walk.area`; углы, где край грядки вне лужайки (у горизонта), пропускаются.
  `depth` 1 (или последняя, если глубин меньше), без `via` и `bush`, время `HELLOWIN_ZOMBIE_DURATION`, очки
  `HELLOWIN_ZOMBIE_POINTS`.
- **Хранение**: `hellowin:flyer:{id}` — летун со временем запуска, TTL = полёт + 10 с; индекс `hellowin:flyers`
  (id → момент окончания полёта) пишут тикер и RPC `flyer.special`, поэтому под RR-локом `flyers`; учёт улетевших
  убирает из индекса только свои id, перечитав его под локом.
- **Выстрел** — RPC `shoot {flyer}`: под RR-локом `flyer:{id}` ключ есть, летуна можно сбить и полёт не кончился → удалить ключ → попадание:
  `flyers + 1`, `points + очки` игроку, одно событие `shot`, `hellowin_flyers_shot_total{depth}`, `+1` в `hellowin:shot`
  раунда (для разоблачения). Иначе промах.
  Выстрел принимается до 500 мс после конца полёта: клиент начинает рисовать летуна, когда событие дошло.
- **Улетевшие** (тикер, каждый тик): летуны из индекса, чей полёт кончился больше 500 мс назад, — под тем же локом:
  ключ ещё есть → удалить, `hellowin_flyers_escaped_total{depth}`; ключа нет — его сбили. Из индекса — в любом случае.
  Ключ удаляет ровно один из двоих (выстрел или учёт), поэтому летун не бывает и сбит, и улетел, и не считается дважды.
  Если тикер лежал дольше запаса TTL, ключи истекают сами и такие летуны не попадут ни в одну метрику.
- Летуны не зависят от ритуала: летают в любой сцене, включая финальную; `round` в событиях — только потому, что его
  несёт каждое событие. Есть ли подключённые клиенты, тикер для летунов не проверяет: запуск без зрителей стоит одного
  ключа в KV и одной публикации.

## Фигурки на поле

Правила — [`players.md`](players.md), «Персонаж», «На поле»; события и RPC — [`protocol.md`](protocol.md).

- **Хранение**: один ключ `hellowin:walkers` — игрок → `{name, look, walk, seenAt, clink?, clinkedAt?, item?, clinked?,
  takeAt?}` (`item`, `clinked`, `takeAt` — бар, см. «Бар»), меняется под RR-локом `walkers`.
  Один ключ — снимок читает фигурки одним запросом; сброс раунда его не трогает, позиции переживают сброс. `name` и
  `look` копируются из записи игрока при выходе на поле и повторном `register`.
- **Выход на поле**: `register` с `look` (или повторный `register` игрока, у которого `look` уже есть) — фигурка
  появляется или переодевается на месте, событие `walker`. Новая фигурка стоит в случайной точке полосы `walk.spawn`
  (`app/config/hellowin.php`) у нижнего края зоны, приведённой в зону. `move` игрока с `look`, чьей фигурки ещё нет
  на поле, сначала ставит её (`walker`), потом ведёт (`move`).
- **Ход** (`move {x, y}`): зона (`Domain/Walk/WalkZone`) — прямоугольник минус набор препятствий (`Obstacle`:
  эллипс `Ellipse`, прямоугольник `Box`); на лужайке препятствие одно — эллипс грядки `walk.patch`, в баре — столы и
  стойка `walk.bar.obstacles`. Цель приводится в зону: в прямоугольник, а из препятствия — на его край (у эллипса — по
  лучу из центра, у прямоугольника — на ближнюю сторону); если этот край вне прямоугольника — в ближайшую точку, где
  край препятствия пересекает сторону прямоугольника. Начало — где фигурка сейчас по её `Walk` и серверным часам. Если
  отрезок не заходит внутрь ни одного препятствия — путь прямой; иначе — кратчайший путь (Дейкстра) по графу
  видимости: вершины — точки вокруг каждого препятствия (у эллипса — на эллипсе, увеличенном на 3 %, через 15°, у
  прямоугольника — углы, отодвинутые на 0,5), лежащие в прямоугольнике (выходящие не больше чем на 2 % прижимаются к
  краю) и вне других препятствий; ребро — отрезок, не заходящий внутрь ни одного препятствия. Запас 3 % держит хорды
  вне грядки и столов. Координаты — до сотых. Длительность — длина ломаной / `HELLOWIN_WALK_SPEED`. Зону сцены
  (лужайка или бар) `WalkService` выбирает по сцене, прочитанной под локом `walkers`, — ход не попадёт в локацию,
  которую зал только что покинул. Под локом `walkers`: два `move` одного игрока не теряют друг друга.
- **Смена локации** (бар ↔ грядка): после перехода из бара (`TransitionHandler::scene`, сцена 0 → 1) и после сброса,
  ведущего в бар (`ResetService`), `WalkService::relocate` под локом `walkers` ставит каждую фигурку в ближайшую
  к её текущей позиции точку зоны новой сцены — стоящей, без пути, недошедшие чоканья и `bar.take` снимаются. Список
  фигурок уходит в самом событии `scene` / `reset` (`walkers`), а не отдельными `move`: другая локация, клиент меняет
  всех сразу. Лок `walkers` занят — сцена или раунд уже сменились, событие уходит без `walkers`. Новые фигурки в баре
  появляются в полосе `walk.bar.spawn`.
- **Уход — presence Centrifugo + тикер.** У канала `hellowin` включён presence (`docker/centrifugo/config.json`):
  серверная подписка каждого подключения попадает в presence с `user` = `publicId`, при закрытии соединения запись
  сразу пропадает. Раз в секунду тикер спрашивает presence канала через API Centrifugo (RR-плагин `centrifuge`,
  `CentrifugoApiInterface::presence`), сводит записи к набору игроков и сравнивает с фигурками: у присутствующих
  обновляет `seenAt`, игроки с `look` без фигурки выходят на поле (`walker`), фигурки, чьих игроков нет дольше
  `HELLOWIN_WALK_LEAVE_AFTER` мс, уходят (`leave`). Несколько вкладок — несколько записей presence одного `user`:
  фигурка одна, уходит, когда закрыта последняя. Задержка ухода нужна, чтобы перезагрузка страницы не роняла фигурку
  и не переносила её к нижнему краю.
- Почему так: presence — готовый в Centrifugo учёт подключений, который сам чистится при разрыве; приложению не нужно
  держать свои счётчики клиентов или heartbeat. Альтернатива — refresh proxy (connect отдаёт `expire_at`, Centrifugo
  периодически продлевает подключение через приложение, тикер удаляет непродлённых) — работает и без presence, но уход
  виден только по истечении срока, а это лишний прокси и запись в KV на каждое продление. Подключение с `look` выходит
  на поле не в connect proxy, а по presence: в момент connect клиент ещё не подписан на канал и своё событие `walker`
  не получил бы.
- **Предмет в руке** — `items` в `app/config/hellowin.php`, по номеру сцены (`null` — пустые руки, за концом списка —
  тоже `null`); в финале — `finale_items` там же, по шагу: запись действует со своего шага до следующей записи, шаги
  до первой записи оставляют предмет сцены (сейчас `[5 => 'beer']`). Считает `Domain/Walk/Items::held(scene, finale)`.
  Вне бара `item` фигурки не хранится: в снимке и событии `walker` это предмет текущей сцены и шага финала; в баре —
  свой у каждой, из записи фигурки (`beer` или пустые руки, см. «Бар»). При смене сцены
  или шага `walker` не рассылаются: событие `scene` или `finale` несёт новый `item`, и клиент меняет предмет у всех
  фигурок сразу.
- Сбой опроса presence (Centrifugo недоступен) — ошибка в лог, фигурки не трогаются: недоступный presence не значит,
  что все ушли.
- **Чоканье по клику** (RPC `clink`, `WalkService::clink`; правила — [`scenario.md`](scenario.md), «Чоканье»).
  Проверки по порядку: фигурка игрока на поле (`no character`), шаг финала 5+ (`Story::cursed`, `not cursed`), цель
  (`no target`): чужая фигурка в `hellowin:walkers` или тыква с `reachable`. **Досягаемость** считает конфиг при сборке
  элементов (`HellowinConfig::getElements`): тыква не дальше `walk.reach` процентов экрана от зоны прогулки
  (`WalkZone::distance` — до ближайшей точки лужайки, `clamp`); с раскладкой по умолчанию это девять тыкв у края грядки.
  **Точка встречи**: у тыквы — со стороны её кружки, наружу от корня грядки (`sign(x − walk.patch.cx)`, ровно над корнем — по `crc32(id)`: нечётный — слева; как `mug` в `public/js/pixel/scene.js`): ближайшая точка лужайки не ближе `walk.clink_gap` по x в ту сторону (`WalkZone::nearestBeside` — перебор края грядки через 0,5°, сторон прямоугольника и вертикали на `clink_gap` с шагом 0,25), а если такой нет в пределах `walk.reach` — ближайшая к тыкве точка лужайки (`clamp`); у фигурки — сбоку от конца её пути (где стоит или куда
  идёт), на `walk.clink_gap` по x со стороны подошедшего, приведённая в зону, а если край лужайки прижал её к цели —
  с другой стороны (`WalkZone::beside`). Путь — тот же `WalkZone::route`, событие — обычный `move` с полем `clink`.
  Под локом `walkers` фигурке пишется **ожидающее чоканье** `clink {kind, target, dueAt, since}`: `dueAt` — прибытие
  подошедшего, а если цель ещё идёт — позднее из двух прибытий; `since` — `startedAt` пути цели в момент клика.
  Любой новый путь фигурки (`move`, другой `clink`, разбегание) запись затирает — так новый ход отменяет недошедшее.
- **Проверка по прибытии — тикер, каждый тик (200 мс)**: читает `hellowin:walkers` без лока и, только если у кого-то
  наступил `dueAt`, берёт лок `walkers` и для каждой такой записи решает: чоканье случилось, если мир всё ещё проклят и
  цель на месте — тыква всегда, фигурка — если она на поле и `startedAt` её пути равен `since` (не пошла заново).
  Запись в любом случае снимается, у случившегося ставится `clinkedAt`; события `clink` (`toast` — случайное
  0…2³¹−1, `at` — время тика) публикуются после лока. Снятие записи под локом и один тикер с лизингом дают ровно одно
  событие на чоканье (сбой публикации теряет его, а не повторяет). Почему так: запись лежит в Valkey рядом с фигуркой
  и переживает перезапуск воркеров и тикера — новый тикер найдёт просроченную и решит её на первом тике; тикер уже
  крутится каждые 200 мс, точности хватает. Альтернатива — отложенная задача RR jobs с `delay`: точнее по времени,
  но memory-очередь теряет её на рестарте, а отмену новым ходом всё равно пришлось бы проверять по записи.
- **Пока чоканье играет** (`walk.clink_duration` мс от `clinkedAt`, по длине анимации фронтенда), новый `clink` того
  же игрока — `busy`, не очередь: так проще и объяснимо, а игрок просто кликает ещё раз. `move` не ограничен.
  `walk.reach`, `walk.clink_gap`, `walk.clink_duration` — раскладка в `app/config/hellowin.php`, не env, как `area`.

## Бар

Правила — [`scenario.md`](scenario.md), «Сцена 0 — «Бар»»; сообщения — [`protocol.md`](protocol.md), «Бар».

- **Где бар.** `RitualPolicy::bar(scene)` — сцена 0, если первый элемент `HELLOWIN_SCENE_STAGE_MAX` равен 0. Тыквы в
  баре `locked` (`ClickHandler` проверяет сцену под локом тыквы — одно чтение `hellowin:scene`), костёр и круг закрыты
  политикой, летунов нет (пустые первые наборы env). Геометрия — `walk.bar` (`BarLayout`): `WalkService` выбирает
  зону бара или лужайки по сцене, прочитанной под локом `walkers`; новые фигурки в баре — в полосе `walk.bar.spawn`.
- **Стойка** — ключ `hellowin:bar` `{mugs, pouring: {since, until, rumor?} | null, emptyAt?}` под RR-локом `bar`
  (`Domain/Bar/BarStore`). **Розлив по одной** ведёт тикер (`BarService::pour`, каждый тик): без лока читает стойку и,
  только если пора (налитая кружка с наступившим `until` или `pouring = null` при `mugs < max`), берёт
  лок, снова проверяет, что сцена — бар, заново считает `max`, ставит кружку (`mugs + 1`, событие `mugs` с `max`) и начинает следующую
  (`pouring = {since: now, until: now + HELLOWIN_BAR_POUR_MS}`, событие `pour`; с вероятностью
  `HELLOWIN_BAR_RUMOR_CHANCE` — `rumor`, случайное 0…2³¹−1). Состояние в Valkey и серверное время: перезапуск воркеров
  или тикера продолжает ту же кружку, а все зрители видят одну фазу пены. Вне бара тикер не наливает.
- **Максимум кружек** (`BarService::max`) — `max = clamp(число фигурок в hellowin:walkers, 1, HELLOWIN_BAR_MUGS)`: тот
  же счёт, что у «пить одному». Не хранится — считается при каждом решении о доливе: в `pour` — чтением `walkers` без
  лока лужайки внутри лока `bar`, в `takes` — по фигуркам, уже взятым под локом `walkers`. Лок лужайки ради счёта не
  берётся: пришедший или ушедший между тиками игрок сдвигает следующий долив, а не налитую кружку. Ушли игроки —
  кружки сверх `max` не убираются, сова просто не доливает, пока `mugs` не станет меньше `max`. `max` — в `bar` снимка,
  в событии `mugs` и в `reset.bar`.
- **«Взять»** (`bar.take`, `WalkService::toCounter`): под локом `walkers` — фигурка на поле (`no character`), сцена —
  бар (`not bar`), в руке не пиво (`has beer`); путь к ближайшей свободной точке отрезка `walk.bar.counter`
  (`BarLayout::atCounter`: от ближайшей точки наружу с шагом `walk.clink_gap` — ширина фигурки, первая не ближе шага
  к концу пути любой другой фигурки на отрезке, то есть стоящей у стойки или идущей к ней; свободной нет — ближайшая) и **ожидающее
  «взять»** `takeAt` = прибытие в записи фигурки (событие — обычный `move`). Любой новый путь (`move`, `clink`, новый
  `bar.take`) запись затирает. **По прибытии** — тикер (`BarService::takes`, каждый тик): без лока ищет наступившие
  `takeAt`; есть — лок `walkers`, внутри него лок `bar` (порядок всегда такой), и для каждой дошедшей фигурки: сцена —
  бар и на стойке есть кружка → `mugs − 1`, у фигурки `item: beer`, `clinked: false` (событие `take` с `ok: true` и
  оставшимися `mugs`); кружки нет → `take` с `ok: false` и реплика `bar-empty`, если с прошлой прошло не меньше 20 с
  (`emptyAt` в записи стойки). Запись снимается в любом случае; если на стойке появилось место — сразу `pour`. Это и
  есть **«последнюю кружку забирает первый»**: проверка и списание — один шаг под локом `bar`, как «сбит ли летун» у
  выстрела; второй дошедший видит уже пустую стойку. Почему ожидание в записи и тикер — как у чоканья по клику: запись
  переживает перезапуски, тикер уже крутится раз в 200 мс.
- **Чоканье в баре** (`WalkService::clink`, `clinks`): как в проклятом мире, но только `{walker}`, у обоих `beer`
  (`no beer` — у себя, `no target` — у цели), зона бара; по прибытии пиво должно быть у обоих — тогда событие `clink` и
  `clinked: true` у **обоих**. **`clink.auto {walker}`** (`WalkService::clinkAuto`): под локом `walkers` — в баре, у
  вызвавшего и партнёра пиво, расстояние между их позициями сейчас не больше `walk.bar.clink_reach` — `clinked: true`
  только вызвавшему, без событий: автоматическое чоканье рисует каждый браузер сам, и сервер не даёт одному браузеру
  засчитать его за другого.
- **«Выпить»** (`drink`, `BarService::drink`): под локом `walkers` — фигурка, бар, `beer` (`no beer`), `clinked` —
  или фигурка на поле одна, по тем же `walkers`, что видит клиент (`not clinked`) → руки пустые; затем `drinks + 1` игроку (`player:{id}`), `+1` в `hellowin:drinks` `{round, count}`
  (под локом `bar`; счёт другого раунда читается как 0 — сброс его не трогает), события `drink` и `drinks`.
- **Цель и готовность.** Цель — `barTarget` в сюжете `hellowin:story` (рядом с `k`, переживает сброс; `null` —
  `HELLOWIN_BAR_DRINKS`). `bar.target {delta}` меняет её под локом `scene` (не ниже 1; вернувшаяся к env — снова
  `null`), событие `drinks`. Бар готов, когда `drunk ≥ target` (после `drink` или понижения цели) или по `bar.ready`:
  `RitualStore::markReady(round, 0)` под локом `scene` — один раз за раунд, событие `ready` и реплика `bar-intro`.
  `scene.next` из бара без готовности — `not ready` (или `force`), как в других сценах.
- **Выход из бара и сброс.** `TransitionHandler::scene` (0 → 1): стойка пустеет (`{mugs: 0, pouring: null}`), фигурки
  переставляются на лужайку с пустыми руками (`relocate`, см. «Фигурки на поле»), `walkers` — в событии `scene`.
  `ResetService` (сброс ведёт в бар): фигурки — на пол бара с пустыми руками, стойка полная (`mugs = max` на момент сброса,
  `pouring: null`), событие `reset` несёт `walkers` и `bar`.

## Модератор

- **Роль.** `ConnectService` сравнивает `moderatorSecret` из `data` подключения с `HELLOWIN_MODERATOR_SECRET`
  (`hash_equals`) и при совпадении кладёт `{moderator: true}` в **meta** подключения. Meta хранит Centrifugo, клиенту
  она не видна; в каждый RPC proxy Centrifugo добавляет её сам (`rpc.proxy.include_connection_meta` в
  `docker/centrifugo/config.json`), поэтому клиент не может назначить себе роль запросом. `RPCService` читает роль из
  meta и отвечает на RPC пульта не модератору `forbidden`. Пустой секрет в env — роли нет ни у кого.
- Почему meta, а не `user`: модератор может быть и игроком (у него свой `playerSecret`), а `user` — это публичный id
  игрока в событиях и presence.

## Сюжет

Правила — [`scenario.md`](scenario.md), «Модератор и сова», «Финал»; RPC пульта — [`protocol.md`](protocol.md).

- **Состояние** — ключ `hellowin:story`: `{ready, finale, paused, zombies, lastPumpkin, bonfire, k, barTarget}` (`Domain/Story/Story`;
  `k` — множитель порогов, вне 0,1–10 или нет поля — читается как 1;
  `bonfire` — сцена, в которой открыт костёр, чтобы `bonfire-open` прозвучал один раз), пишется
  только под RR-локом `scene`, читается снимком вместе с раундом и тыквами одним `getMultiple`. Один лок со сценой —
  поэтому сброс (он берёт `scene`, все `pumpkin:{id}`, `bonfire` и `circle`) атомарно возвращает и сюжет; пауза и `k` при этом остаются.
- **Пульт** (`Application/Story/StoryService`): `finale.step`, `pause`, `zombies`, `thresholds` меняют сюжет под локом через
  `RitualStore::updateStory` и сравнивают «до» и «после»: событие и реплика уходят только при изменении, поэтому повтор
  нажатия безопасен. Шаг финала меняется, только если запрошен следующий (`Story::stepTo`). `owl.say` ничего не хранит —
  только публикует.
- **Множитель порогов** (`k`): действующий порог — `RitualPolicy::threshold($type, $k)` = `max(1, round(базовый × k))`,
  базовые — `HELLOWIN_CLICKS_PER_STAGE`, `HELLOWIN_BONFIRE_CLICKS_PER_STAGE`, `HELLOWIN_CIRCLE_CLICKS_PER_STAGE`. Клик
  читает `k` из сюжета под локом элемента вместе с `round` и `scene` (`ClickOutcome::$k`) и по нему же решает о переходе
  и шлёт `threshold` в `click`; снимок умножает `threshold` по `k` из того же `getMultiple`. Смена `k` ничего не
  пересчитывает и задач не ставит: элемент, у которого `clicks` уже не меньше нового порога, двинется со следующим
  кликом — тем же путём и с тем же ключом `{round}:{id}:{toStage}`, один переход на стадию; излишек сгорает, как обычно.
- **Разбегание** на шаге финала 2 (`Story::SCATTER_STEP`): после события `finale` и реплики `finale-2`
  `WalkService::scatter` под локом `walkers` ведёт каждую фигурку с её текущей точки к краю лужайки — по лучу от центра
  грядки через фигурку до стороны прямоугольника `walk` (`WalkZone::outward`), путь — тем же `WalkZone::route`, что у
  RPC `move`, — и публикует обычный `move` каждой. Повтор шага ничего не меняет, поэтому и разбегание одно. Лок лужайки
  занят — фигурки остаются на местах, шаг всё равно сделан (это украшение, а не состояние сюжета).
- **Аптайм** (`Domain/Clock/StartTime`, `startedAt` в снимке): время запуска RoadRunner. Первый воркер при загрузке
  (`HellowinBootloader::boot`) пишет текущее время в ключ `hellowin:started-at` KV-хранилища `process` — драйвер
  `memory` RR, живёт в процессе RoadRunner — если ключа ещё нет, под RR-локом `started-at`; следующие только читают.
  Поэтому перезапуск PHP-воркеров его не сбрасывает, а перезапуск RoadRunner (контейнера `app`) — сбрасывает. Не
  Valkey: тот переживает перезапуск `app`, и аптайм считался бы от первого запуска стека. Отсчёт — от загрузки
  первого воркера, а не от старта самого процесса RR: разница — секунды запуска пула.
- **Разоблачение** (`Domain/Story/Reveal`, `Application/Story/RevealBuilder`) — числа раунда без отдельных счётчиков
  на клик: у каждой тыквы в записи `hellowin:pumpkin:{id}` есть `accepted` — принятые клики раунда, растёт под тем же
  локом `pumpkin:{id}`, что и `clicks`, и `spent` — сколько кликов взяли её выполненные переходы: задача перехода
  прибавляет min(`clicks`, порог) по `k`, действующему, когда она выполняется. Отсюда: `clicks` = Σ `accepted`; `jobs` =
  Σ `stage` + `scene` (каждая стадия и каждая сцена — ровно одна выполненная задача перехода); `burned` = `clicks` −
  Σ `spent` − Σ min(`clicks`, действующий порог) — переход тратит ровно порог, остальное сгорело на идемпотентности или
  после готовности тыквы, кроме кликов, ещё копящихся к следующему переходу. `spent` в записи, а не `stage` × порог:
  модератор меняет `k` посреди раунда, и каждая стадия стоила свой порог. Запись без `spent` (до появления поля)
  читается как 0 — до сброса `burned` такого раунда завышен. Костёр и круг входят во все три суммы со своими порогами
  и записями: их `accepted` — в `clicks`, стадии — в `jobs`, сгоревшие — в `burned`; клики
  `locked` не принимаются и не считаются нигде. Сбитые летуны — ключ `hellowin:shot`
  `{round, count}` под RR-локом `shot` (`Domain/Story/ShotTally`): выстрелы редки, лок не мешает; счёт другого раунда
  читается как 0, так что сброс его не трогает. Выпитые в баре — `hellowin:drinks` так же (`drinks`, см. «Бар»).
  `lastPumpkin` — игрок из задачи, отметившей последнюю готовность
  (тыквы, костра или круга); анонимная задача отметки прежнего игрока не стирает;
  имя берётся из записи игрока при сборке. `reveal` считается при каждой сборке снимка и событии `finale` с шага 4.

## Поток клика

1. RPC `click {element}` → `RPCService` проверяет элемент по реестру; игрок — `user` подключения (`publicId` или пусто).
2. Под RR-локом `pumpkin:{id}` (у костра — `bonfire`, у круга — `circle`): `clicks + 1` в KV; под тем же локом читаются
   `round` и `scene`. Клик по костру или кругу (центральный элемент, `Element::centrepiece()`) сначала, под тем же
   локом, читает весь ритуал одним `getMultiple` и спрашивает `RitualPolicy::centrepieceOpen` (костёр — тыквы сцены
   готовы; круг — финальная сцена на шаге 0; оба — ниже своей последней стадии сцены); закрыт — ничего не пишет, ответ `locked`, дальше шаги не идут. Проверка под локом
   элемента, а не по снимку до него: сброс берёт и этот лок, так что между проверкой и счётом он не вклинится. Шаг
   финала меняется под локом `scene`, поэтому клик по кругу на самой границе шага 0 → 1 может ещё засчитаться — это
   безвредно: готовность и реплики после шага 0 не отмечаются.
3. Метрика `hellowin_clicks_total{type,element}` — после принятого клика: `busy` и `locked` её не увеличивают.
4. Статистика игрока: под RR-локом `player:{id}` `clicks + 1` (анонимный клик — пропуск). Сбой статистики пишется
   в лог и не ломает клик.
5. Публикация `click` в канал (с `player`, если он есть).
6. Если политика разрешает переход (`clicks >=` действующий порог тыквы — `HELLOWIN_CLICKS_PER_STAGE` × `k` — и
   `stage < stageMax(scene)`; у костра и круга — их порог и потолок, `RitualPolicy::threshold($type, $k)`,
   `stageMax($scene, $type)`) — задача
   `TransitionPumpkin {key, round, pumpkin, toStage, player}` в очередь, метрика
   `hellowin_transition_jobs_pushed_total{kind="pumpkin"}` (у костра — `kind="bonfire"`, у круга — `kind="circle"`).
   Ставится на **каждом** таком клике, пока переход
   не выполнен: дубли намеренные. `player` — вне ключа: из дублей выполняется один, его игрок и «добил» тыкву.

## Переходы

- **Тыква.** Обработчик `TransitionPumpkin` помечен `#[Idempotent(storage: 'transitions', key: 'payload.key')]`
  (пакет `spiral/idempotency`), ключ в payload — `{round}:{pumpkin}:{toStage}`. Внутри: RR-лок `pumpkin:{id}` →
  доменная проверка (`round` текущий и `stage == toStage - 1`) → `stage = toStage`, `spent += min(clicks, порог)`
  (порог — по `k` в момент выполнения; задача, поставленная до смены `k`, выполняется всё равно), `clicks = 0` → лок отпущен →
  `finished + 1` игроку из payload → публикация `pumpkin` (с `player`) → `hellowin_transitions_total{kind="pumpkin"}`, `hellowin_pumpkin_stage{element}` → проверка
  готовности сцены по снимку (`RitualPolicy::sceneReady`) → под RR-локом `scene` отметка `ready` в сюжете, только если
  её ещё нет (две тыквы, добитые одновременно, обе видят сцену готовой — отметит одна) → событие `ready`, реплики
  `last-pumpkin` (игрок из payload) и `scene-ready`. Сама сцена не переходит. Если сцене нужен костёр
  (`RitualPolicy::centrepieceOpen` для костра — тыквы готовы, костёр ниже своей последней стадии сцены), вместо готовности — отметка
  `bonfire` (сцена) в сюжете под тем же локом `scene`, тоже один раз на сцену (`RitualStore::markBonfireOpen`), и
  реплики `last-pumpkin`, `bonfire-open`.
- **Костёр.** Та же задача `TransitionPumpkin` с `pumpkin: "bonfire"`, ключ `{round}:bonfire:{toStage}`; отличаются лок
  (`bonfire`), запись (`hellowin:bonfire`), порог (`HELLOWIN_BONFIRE_CLICKS_PER_STAGE`), потолок
  (`HELLOWIN_BONFIRE_STAGE_MAX`) и метрики: `kind="bonfire"` в `pushed` и `transitions`, gauge
  `hellowin_bonfire_stage`. Переход костра на последнюю стадию сцены делает сцену готовой: `ready`, реплики
  `bonfire-done` (игрок из payload) и `scene-ready`; в `lastPumpkin` сюжета — игрок костра.
- **Круг.** Тот же механизм центрального элемента, что у костра: задача `TransitionPumpkin` с `pumpkin: "circle"`, ключ
  `{round}:circle:{toStage}`, лок `circle`, запись `hellowin:circle`, порог `HELLOWIN_CIRCLE_CLICKS_PER_STAGE`, потолок
  `HELLOWIN_CIRCLE_STAGES` в финальной сцене (0 до неё), метрики `kind="circle"` и gauge `hellowin_circle_stage`.
  Политика двигает тыквы и костёр только до финальной сцены, круг — только в ней. Переход круга на последнюю стадию на
  шаге финала 0 делает финальную сцену готовой: `ready`, реплики `circle-done` (игрок из payload) и `scene-ready`; в
  `lastPumpkin` сюжета — игрок круга. Какую реплику сказать, решает тип элемента (`OwlLine::finished`).
- **Шаг финала 1.** `StoryService::finaleStep(step, force)` под локом `scene`: без `force` шаг 0 → 1 ждёт готовности
  финальной сцены (`Story::awaitsReady` — `ready` в сюжете отмечен), иначе ответ `not ready` и ничего не меняется.
  Остальные шаги — как раньше, по одному.
- **Сцена.** RPC модератора `scene.next {scene, force?}` (`StoryService::nextScene`) по снимку проверяет: `scene`
  текущая, не финальная, готова (или `force`) → задача `TransitionScene {key, round, toScene}`
  (`pushed{kind="scene"}`), ключ `{round}:scene:{toScene}`, тоже `#[Idempotent]`: повторные нажатия ставят дубли,
  выполняется одна. Обработчик: RR-лок `scene` → проверка (`round` текущий и `scene == toScene - 1`) → `scene = toScene`,
  `ready` и `bonfire` сняты, в финальной сцене `finale = 0` → публикация `scene` (со `stageMax`, `bonfireStageMax` и
  `circleStageMax` новой сцены), в финальной — `finale
  {step: 0}`, реплика `scene-{toScene}` → `hellowin_transitions_total{kind="scene"}`, `hellowin_scene_stage`.
- **Сброс.** `ResetService::reset(?int $fromRound)` (консоль `hellowin:reset [--round=N]`): под локами `scene`
  и всех `pumpkin:{id}`, `bonfire` и `circle` сравнивает текущий `round` с `fromRound` (по умолчанию — текущий); совпал — `round + 1`,
  сцена 0, тыквы, костёр и круг `stage 0`/`clicks 0`/`accepted 0`/`spent 0`, сюжет заново (кроме паузы и `k`), публикация `reset`; не совпал — раунд уже сброшен, ничего не делает. Это
  идемпотентность по `reset:{round}` без пакета: состояние и так защищено этими локами, а сравнение `round` под ними
  отсекает второй сброс того же раунда; ключ в Valkey дал бы второй источник правды о раунде. Сервис вызывается из любого
  места (будущее голосование) — достаточно передать раунд, который хотят завершить.

Ключи идемпотентности в Valkey: `hellowin:amo:` + область (`Класс::handle`) + ключ из payload, например
`hellowin:amo:App\Application\Hellowin\Job\TransitionPumpkin::handle:1:pumpkin-3:2`. `round` в ключе обязателен:
без него после сброса те же переходы были бы отсечены, пока живы старые маркеры.

Гарантия для переходов — **AtMostOnce** («не более одного раза»): маркер ключа пишется до эффекта, дубль не вызывает
обработчик, задача подтверждается (ACK). Цена — если воркер упадёт между маркером и эффектом, переход потерян, а новые
задачи с тем же ключом отсекаются, пока маркер жив: тыква «застревает» на пороге. Поэтому TTL маркера короткий — 300 с:
после истечения следующий клик снова запускает переход, а от двойного перехода защищает доменная проверка `stage`.

Очередь подключена по скиллу пакета: `QueueIdempotencyBootloader`, `transports.queue` = `QueueRetryMiddleware`,
`QueueKeyMiddleware`; в `app/config/queue.php` `interceptors.consume` — `ErrorHandlerInterceptor`,
`RetryPolicyInterceptor`, `IdempotencyInterceptor` (retry снаружи). У AtMostOnce-хранилища занятый ключ — это дубль:
claim возвращает nil, обработчик не вызывается, задача подтверждается. Путь `LockedException` →
`RetryableLockException` → повтор с задержкой относится к lease-хранилищам (AtLeastOnce) и сработает, только если
alias `transitions` переключить обратно на `RedisLeaseConfig`.

## Лимиты запросов

Основная нагрузка игры — RPC через Centrifugo; HTTP — две страницы и статика.

- **RPC** — в PHP, потому что HTTP-лимитер RoadRunner их не видит, а лимиты команд Centrifugo есть только в PRO.
  `RPCService` до любого метода, кроме вызовов модератора, берёт токен из ведра (token bucket): ведро держит до
  `burst` токенов и пополняется на `rate` в секунду. Ключ — игрок (`user` подключения), без игрока — id подключения;
  группа — `click`, `shoot`, `move` или `other` (все прочие методы). Пустое ведро — ответ `rate limited` и
  `hellowin_rpc_rate_limited_total{group}`. Вёдра лежат в KV `process` (память RoadRunner: лимиту не нужна
  долговечность, рестарт воркеров их не теряет) под ключом `hellowin:rate:{group}:{caller}` с TTL на время полного
  пополнения плюс секунда (KV округляет срок до секунд, а пропавшее раньше ведро выдало бы лишний `burst`). У KV нет
  атомарного обновления, поэтому чтение и запись ведра — под RR-локом `rate:{group}:{caller}` (ожидание 0.5 с). Сбой
  лимитера (лок, KV) пишется в лог и пропускает вызов: лимит защищает игру и не должен её ронять.
- **Подключения** — Centrifugo OSS: `client.user_connection_limit` (10 подключений на игрока) и
  `client.connection_rate_limit` (100 новых подключений в секунду на узел), [`infra.md`](infra.md).
- **HTTP** — middleware `rate_limiter` RoadRunner, по IP, только для PHP-страниц: статику отдаёт `static` раньше
  него ([`infra.md`](infra.md)).

Значения по умолчанию (`HELLOWIN_RPC_RATE_*`, «Env») рассчитаны так, чтобы быстрые клики (10–15 в секунду) не
резались никогда, а поток из скрипта упирался в `burst` и дальше шёл не быстрее `rate`.

`spiral/idempotency` подключён из ветки `feat/redis-at-most-once` (`dev-feat/redis-at-most-once as 0.5.0`) до релиза
0.5 с `RedisAtMostOnceConfig`; после релиза — обычная версия `^0.5`. Valkey с AOF и volume — состояние переживает
рестарт `app` и `valkey`; отсутствующий ключ `hellowin:round` означает раунд 1. Задачи в очереди при рестарте `app`
теряются — следующий клик сверх порога ставит переход снова.

Почему не SQL: данных мало, живут одно мероприятие, сложных выборок нет.

| `hellowin_transition_jobs_pushed_total{kind}` | counter | задачи перехода в очереди, дубли включительно; `kind` = `pumpkin` / `bonfire` / `circle` / `scene` |

| `hellowin_circle_stage` | gauge | стадия магического круга (по той же причине) |
| `hellowin_players` | gauge | известные игроки (с секретом, с именем и без); выставляет тикер при сборке таблицы лидеров |
| `hellowin_players_registered` | gauge | игроки с именем; там же |

Плюс встроенные `rr_*` и `centrifugo_*`. Ошибки метрик клик не ломают.
