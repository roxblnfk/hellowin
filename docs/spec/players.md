# Игроки и статистика

Статус: идентификация, имя (`register`), своя статистика (`me`), атрибуция кликов и «добитых» тыкв, хранение —
**реализовано** на backend, таблица лидеров — тоже; клики по сценам и участие в раундах — **запланировано**.

## Идентификация

- При первом визите браузер генерирует секрет (UUID) и хранит его в `localStorage`. Секрет знает только этот браузер —
  по сути это пароль игрока. Наружу (в события, разметку, логи, метрики) он не уходит.
- Секрет передаётся только в `data` подключения к Centrifugo: `{playerSecret}`. Допустимый секрет — 16–128 символов
  `A-Z a-z 0-9 -` (UUID подходит); иначе подключение анонимное.
- `ConnectService` вычисляет `publicId` — первые 16 hex-символов SHA-256 от секрета (с префиксом домена
  `hellowin:player:`), и отвечает `user: publicId`. Дальше Centrifugo сам подставляет пользователя в каждый RPC —
  клиент не шлёт ID в запросах и не может выдать себя за другого. 64 бита хеша хватает, чтобы игроки одного
  мероприятия не совпали; восстановить секрет из `publicId` нельзя.
- Без секрета подключение анонимное (`user` пустой): клики анонимов считаются в ритуале и метриках, но без
  статистики игрока и без поля `player` в событиях.
- Имя: RPC `register {name}`. Имя обрезается по краям; 1–24 символа: буквы, цифры, пробел (не двойной), `_ . -`,
  хотя бы одна буква или цифра. Иначе `invalid name`; анонимное подключение получает `anonymous`. Имена не уникальны:
  игрока определяет `id`. Без имени игрок играет анонимно (`name` — `null`), статистика всё равно копится.
- Своя статистика при загрузке: RPC `me` → `{ok:true, player, top}` (`null`, если игрок ещё ничего не сделал или
  подключение анонимное). `register` отвечает тем же объектом. Формат — [`protocol.md`](protocol.md).

## Статистика

Запись игрока: `{id, name, clicks, finished, flyers, points}`.

- `clicks` — принятые клики по тыквам.
- `finished` — «добитые» тыквы. «Добил тыкву» — тот, чья задача `TransitionPumpkin` реально выполнилась: задача несёт
  `player` поставившего её клика (вне ключа идемпотентности), а из k+n дублей выполняется одна — так идемпотентность
  честно выбирает победителя. Событие `pumpkin` несёт этого игрока.
- `flyers`, `points` — сбитые летуны и очки за них ([`scenario.md`](scenario.md), «Летуны»).

Статистика вторична по отношению к игре: если запись игрока не удалось обновить (лок занят, KV недоступен), действие
выполняется без игрока, ошибка пишется в лог.

## Хранение

Всё — RR KV-плагин на Valkey (драйвер `redis`, storage `hellowin`), без SQL:

- запись игрока `hellowin:player:{publicId}` — `{id, name, clicks, finished, flyers, points}` (сериализует KV-плагин,
  как и состояние ритуала), изменяется под RR-локом `player:{publicId}` (конкуренции за него почти нет);
- индекс игроков `hellowin:players` — список `publicId`, дописывается под локом `players` только при появлении
  нового игрока (первое действие или `register`), а не на каждом клике;
- таблица лидеров — тикер ([`engine.md`](engine.md), «Периодический процесс») раз в `HELLOWIN_LEADERBOARD_INTERVAL` мс
  читает игроков по индексу, ранжирует (очки, затем «добитые» тыквы, затем клики; без действий — не попадают),
  оставляет `HELLOWIN_LEADERBOARD_SIZE` лучших, пишет ключ `hellowin:leaderboard` и публикует событие `leaderboard`.
  RPC `me` отдаёт последнюю сборку из ключа — таблица видна сразу после загрузки.

RR KV не умеет атомарный инкремент, сортированные множества и обход ключей — отсюда локи, индекс и агрегирующий
процесс. Это осознанный выбор: демо показывает связку KV + локи + очередь RoadRunner, а не нативные структуры Valkey.
